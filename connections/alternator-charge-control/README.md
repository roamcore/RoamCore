# Alternator charge control (Wakespeed / smart regulator — vendor-neutral alternator charge umbrella for HA)

**Tier:** B (recipe)
**Category:** power
**Status:** beta

## What this connection is

Alternator charge control — the umbrella for "did the alternator top off the house battery while I drove today + should it be charging right now?" — is the alternator-side complement to the broader RoamCore power-side intelligence. The single "is the alternator allowed to charge right now?" tile aggregates the operator's chosen charge mode + ignition state + battery SOC + battery temperature + the Stealth / Sleep mode flag + the regulator's fault state into one dashboard indicator; the "charge mode" selector is the operator-facing policy choice (one of `off` / `auto` / `boost` / `float` / `desulfation` / `stealth` / `protect_battery`); the "target voltage" tile surfaces the regulator's voltage setpoint (V); the "charge current" tile surfaces the current accepted by the house battery bank during alternator charging (A — derived from the upstream regulator's current-sense input OR the Victron `sensor.rc_power_battery_current_a`); the "temperature-compensation active" tile is the cold / hot battery gate (TRUE iff the temperature probe reads cold or hot AND the regulator's temperature-compensation curve is actively lowering the target voltage); the "fault" tile is the regulator's fault trip gate (TRUE iff the regulator reports over-temp / over-voltage / communication lost / BMS lockout — the §8.6 fault-block automation forces charging OFF + notifies the operator when this tile is TRUE); the "last trigger reason" tile surfaces the reason the alternator was last enabled (one of `manual` / `ignition_on` / `soc_low` / `battery_cold` / `boost` / `desulfation` / `stealth_suppressed` / `fault_blocked`); the "manual override" button is the manual override (the operator can force alternator charging ON for a configurable duration from the dashboard, regardless of the auto-policy — useful when the operator knows they need a top-off before tonight).

RoamCore ships **no** native alternator regulator. We RECIPE the well-understood combination of FOUR upstream operator-side paths and a translation layer that maps each upstream `switch.*` (Path A1 / Path A2 / Path B regulator enable + Path C1 / Path C2 relay) + upstream `sensor.*` (Path A1 / Path A2 / Path B target voltage + charge current + battery temperature) + upstream `binary_sensor.*` (ignition-signal-only + fault state) into a vendor-neutral `rc_power_alternator_*` contract layer. The four paths:

- **Path A — Smart alternator regulator linked to a Victron / Renogy / REDARC / Sterling / Balmar / EP-Power DC-DC charger** (recommended for operators whose alternators already charge through a DC-DC charger with its own regulator control). Path A1 — Victron Cerbo GX + DC-DC charger via the HA core `victron` integration (the canonical Victron integration since 2022.x surfaces a `switch.*` enable/disable entity + `sensor.*` telemetry + `binary_sensor.*` fault state on the DC-DC charger). Path A2 — Renogy / REDARC / EP-Power / Sterling / Balmar DC-DC charger via the HA core `mqtt` integration (since 2022.x surfaces the vendor's Bluetooth-to-MQTT bridge topic).

- **Path B — Generic smart alternator regulator exposed over MQTT by the vendor's bridge** (Wakespeed WS500 / Balmar MC-618 / Sterling Regulated Advanced Alternator-to-Battery charger / Renogy Battery-to-Battery / REDARC BCDC / EP-Power B2B / ARCO Zeus / OEM CAN-j1939 regulator with a CAN-to-MQTT bridge such as Wakespeed's WS Link / Sterling's BMS Link / Balmar's Smartlink / Renogy's BT-2 / REDARC's RedVision / EP-Power's EP Link / a Signal K gateway on the boat's NMEA 2000 backbone). The operator pairs the regulator with the bridge + wires the bridge's MQTT topics into HA via the HA core `mqtt` integration (since 2022.x). The recipe shows the upstream `switch.*` + `sensor.*` + `binary_sensor.*` + `number.*` + `select.*` family being wired through `template:` wrappers into the contract layer.

- **Path C — Relay / GPIO switch between the alternator field wire and a plain smart charger** (the minimum-viable path for operators with no smart regulator + no MQTT bridge — a plain externally-regulated alternator whose field excitation wire can be turned off). Path C1 — Shelly 1 / Shelly Plus 1 wired to the alternator's field excitation wire + the HA core Shelly integration (since 2022.x). Path C2 — ESPHome / Tasmota GPIO relay driven by an ESP32 / ESP8266 node + the upstream ESPHome integration.

- **Path D — Read-only ignition-signal-only + no control** (the alternator is dumb / the operator does NOT want to control the alternator at all — just knows when the engine is running). The operator uses an upstream `binary_sensor.rc_vehicle_engine_running` from the vehicle-related connection slices OR a GPIO on an ESPHome node + a voltage divider on the alternator's D+ / IGN wire.

All four paths land on the same vendor-neutral contract layer via 8 `rc_power_alternator_*` dashboard tiles:

- `binary_sensor.rc_power_alternator_charging_enabled` — the AND gate (TRUE iff the alternator is allowed to charge right now — combines `select.rc_power_alternator_charge_mode != off` + ignition ON + battery SOC > threshold + temperature within range + `select.rc_mode` not suppressed + fault clear).
- `select.rc_power_alternator_charge_mode` — the operator's chosen charge mode (one of `off` / `auto` / `boost` / `float` / `desulfation` / `stealth` / `protect_battery`).
- `sensor.rc_power_alternator_target_voltage_v` — the regulator's voltage setpoint (V; the temperature-compensation may have lowered it from the operator's chosen nominal voltage).
- `sensor.rc_power_alternator_charge_current_a` — the current accepted by the house battery bank during alternator charging (A; derived from the upstream regulator's current-sense input OR the `sensor.rc_power_battery_current_a` from the Victron `connections/victron/` recipe).
- `binary_sensor.rc_power_alternator_temp_compensation_active` — the cold / hot battery gate (TRUE iff the temperature probe reads cold or hot AND the regulator's temperature-compensation curve is actively lowering the target voltage).
- `binary_sensor.rc_power_alternator_fault` — the regulator's fault trip gate (TRUE iff the regulator reports over-temp / over-voltage / communication lost / BMS lockout — the §8.6 fault-block automation forces charging OFF + notifies the operator when this tile is TRUE).
- `sensor.rc_power_alternator_last_trigger_reason` — the reason the alternator was last enabled (one of `manual` / `ignition_on` / `soc_low` / `battery_cold` / `boost` / `desulfation` / `stealth_suppressed` / `fault_blocked`).
- `button.rc_power_alternator_manual_override` — the manual override (the operator can force alternator charging ON for a configurable duration from the dashboard).

This fills the `alternator` subsystem slot under the existing `power` subsystem in `docs/reference/rc-entity-naming.md` — a forward-compatible addition that mirrors how `hvac` was added by the heated-floors slice + how `mode` was added by the mode slice. The contract tile ids stay vendor-neutral — NO Wakespeed / Balmar / Sterling / Renogy / REDARC / EP-Power / ARCO / OEM names leak into the tile ids.

RoamCore does **not** ship an alternator regulator, a relay, a temperature probe, an ignition signal, an ESPHome node, or any vendor-specific controller. The HA core `mqtt` integration + the HA core Shelly integration + the HA core `victron` integration + the operator's choice of vendor integration (Path A / Path B) + the upstream `switch.*` (Path C relay) are the upstream truth; RoamCore layers a contract on top: the `rc_power_alternator_*` dashboard tiles + the OpenClaw queries that bind to those contract entities ("is the alternator charging?", "alternator charge mode", "alternator target voltage", "alternator charge current", "is the alternator temperature-compensating?", "is the alternator faulting?", "alternator last trigger reason", "alternator manual override").

## Setup recipe (one-paragraph)

1. Decide which path fits your van: **Path A** — DC-DC-charger-linked regulator (you already have a Victron / Renogy / REDARC / Sterling / Balmar / EP-Power DC-DC charger integrated into HA via the `victron` integration or the vendor's MQTT bridge); OR **Path B** — vendor MQTT bridge (your regulator ships with a Bluetooth / Wi-Fi / CAN-to-MQTT bridge — Wakespeed's WS Link / Balmar's Smartlink / Renogy's BT-2 / REDARC's RedVision / Sterling's BMS Link / EP-Power's EP Link / ARCO's Zeus app / a Signal K gateway on the boat's NMEA 2000 backbone); OR **Path C** — relay / GPIO switch on the alternator field wire (no smart regulator + no MQTT bridge — a plain Shelly 1 / Shelly Plus 1 / Zooz ZEN17 / Aeotec Nano Switch / ESPHome / Tasmota GPIO node interrupts the field excitation wire); OR **Path D** — read-only ignition-signal-only + no control (the alternator is dumb).
2. Wire the prerequisites FIRST (the recipe §2 walks through these — Path A needs the upstream vendor integration configured + the upstream `switch.*` + `sensor.*` + `binary_sensor.*` entities visible; Path B needs the regulator paired with the vendor bridge + the bridge's MQTT topic wired into HA via the HA core `mqtt` integration; Path C needs the relay wired to the alternator's field excitation wire + the Shelly / ESPHome integration configured; Path D needs only the ignition signal). The operator MUST not skip the safety prerequisites — the `binary_sensor.rc_power_alternator_charging_enabled` tile refuses to flip TRUE until all five safety interlocks (ignition on + SOC > threshold + temperature within range + mode not suppressed + fault clear) hold simultaneously.
3. Wire the upstream device. Path A: configure the `victron` integration (Path A1) OR the `mqtt` integration (Path A2); the upstream `switch.*` (charge enable) + `sensor.*` (target voltage + charge current + battery temperature) + `binary_sensor.*` (fault state) appear. Path B: wire the regulator's MQTT topic into HA; the upstream entities appear. Path C: wire the relay to the alternator's field wire + wire the Shelly / ESPHome integration into HA; the upstream `binary_switch.*` (Path C1) OR `switch.*` (Path C2) appears. Path D: wire only the ignition signal.
4. Wire the HA core `template:` switch + sensor + binary_sensor wrappers that synthesize the `rc_power_alternator_*` contract tiles (recipe §3 / §4 / §5 / §6 walk through the template YAML for each path).
5. Create the `rc_power_alternator_*` contract tiles (or import the recipe's `template:` helpers from the recipe §7 helper YAML). The recipe walks through synthesizing each `rc_power_alternator_*` tile from the upstream `switch.*` + `sensor.*` + `binary_sensor.*` + ignition + battery SOC + battery temperature + mode tiles from upstream connections (Victron `sensor.rc_power_battery_soc` + `sensor.rc_power_battery_current_a` + `sensor.rc_power_battery_temperature_c` + mode `select.rc_mode` + vehicle `binary_sensor.rc_vehicle_engine_running`).
6. Verify the six safety interlocks (recipe §8 walks through each): ignition-on enable, SOC-low boost, battery-cold temperature-compensation, mode-aware Stealth / Sleep suppressions, protect_battery mode, fault-block.
7. Enable the recipe §8 automations (engine running → enable alternator charging when SOC < threshold + charge_mode allows + ignition on; SOC-low boost when battery is low; battery-cold temperature-compensation lowering the target voltage; mode-aware Stealth / Sleep suppressions blocking the alternator when the operator has flagged it noisy; protect_battery mode disabling charging when SOC < 20 %; fault-block forcing charging OFF when the regulator reports a fault).
8. Reload the RoamCore dashboard; the `rc_power_alternator_*` contract tiles appear under the Power section.

Full howto with copy-pasteable YAML for the helpers, automations, Path A / Path B / Path C / Path D wiring, the `mqtt:` YAML for Path B, the `template:` wrappers for the contract layer, the six safety interlocks in full, mode-aware exceptions, and the tier-a promotion outline: see [`docs/recipe.md`](docs/recipe.md).

## Why tier-b, not tier-a

Tier-a requires a working RoamCore-owned `config_flow.py`, integration tests against a real alternator regulator + relay + temperature probe + ignition signal bench on CI, and `wizard.one_tap: true`. We have no operator path choice on the CI bench to integration-test against (no alternator regulator, no relay, no temperature probe, no ignition signal, no ESPHome node, no CAN bus bridge). The operator's exact Path A vs Path B vs Path C vs Path D choice + the MQTT topic / GPIO pin / CAN-bridge choice is a wiring decision that requires the operator's physical install context, and there's no canonical RoamCore-owned upstream HA integration that does what this connection recipes. So this connection is honestly beta-tier: the recipe is sound but we cannot claim one-tap automation. The `config_flow: true` field is honest upstream truth (the HA core `mqtt` integration + the HA core Shelly integration + the HA core `victron` integration + the operator's chosen vendor integration all expose a GUI flow since 2022.x) — it is NOT a tier-a marker for RoamCore (a tier-a marker would be a RoamCore-owned operator-wired setup flow + RoamCore-owned integration code + integration tests against a RoamCore-owned bench). The [`tests/test_connection_yml.py`](tests/test_connection_yml.py) file asserts the manifest is honest about its tier — including the `test_safety_interlocks_are_documented` defensive guard for the future tier-a promotion's hard-enforced safety interlock asserts — that's the only test we can ship today.

When a real smart alternator regulator + relay + temperature probe + ignition signal bench lands (a bench with at least one Path A DC-DC-charger-linked regulator OR one Path B vendor MQTT bridge regulator + one Path C Shelly 1 / Shelly Plus 1 relay + temperature probe + ignition signal + the six safety interlock sources that the §11 promotion outline describes), this connection is the candidate to promote to tier-a: add a native `config_flow.py` that walks the operator through Path A vs Path B vs Path C vs Path D + MQTT topic / GPIO pin / CAN-bridge choice + ignition signal declaration, add integration tests that assert the six safety interlocks (ignition-on enable + SOC-low boost + battery-cold temperature-compensation + mode-aware Stealth / Sleep suppressions + protect_battery mode + fault-block) all flip to the expected state when wired to canned fixture responses, and flip `tier_requirements` to include `working_config_flow` + `integration_test_passes` + `no_manual_yaml_required` + `safety_interlocks_hard_enforced_in_roamcore_code`.
